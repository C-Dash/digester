# CDASH Digester — Project Briefing

## What This Is

A PySide6 desktop application that validates, prescreens, and catalogs archival media batches for the CDASH (Cambridge Digital Architectural Survey History) system. It processes batch folders of JPEG, TIFF, and PDF files, checks them against acceptance criteria, and exports CSV catalogs.

## Project Layout

```
src/
  cdash_digester/
    cdash_objects.py     — SQLite data model (BatchDB), name parsers, constants
    digester.py          — Main orchestrator (Digester class); runs on QThread
    prescreener.py       — Per-file acceptance checks; screen_file() is the core function
    repair_media.py      — Auto-repair for known fixable issues (rgba, iphone_vert)
    validator.py         — CDASHValidator for folder/media name rules
    gui/
      main_window.py     — Top-level PySide6 window and toolbar actions
      folder_pane.py     — Left pane: item set folder tree

      thumbnail_pane.py  — Thumbnail preview
      console_window.py  — Log output window
    exif_ex.py           — CLI: dump all ExifTool tags for a file
```

## Naming Conventions

- **Batch folder**: `CDB<YYMMDD>[a-z]?-<name>` (e.g. `CDB260320-Test_batch`)
- **Media folder**: `[F<index>-]<slug>-OF<item_set_id>` (e.g. `F6-Mass_Ave-OF43111`)
- **Media file stem**: `<place_slug>_<doc_index>p<page_index>-<doc_type>[-OP<place_id>]`
  - e.g. `Mass_Ave_0027p0001-VE-OP43296`
- **Doc types**: 2-letter codes — VE (Exterior View), VI (Interior View), RF (Research Form), AI (Architectural Inventory), VP (Plan View), and others — defined in `cdash_objects.DOC_TYPES`

## Data Model (SQLite via BatchDB)

Key tables: `cdash_batch`, `cdash_folder`, `cdash_place`, `cdash_doc`, `cdash_media` (plus the persistent `cdash_folder_cache`/`cdash_place_cache`/`cdash_file_cache`). There is no `cdash_rejects` table — rejected/repaired activity is tracked in `catalog/repair_reject.csv`, not the DB.

`cdash_media` important columns:
- `ready` INTEGER (0/1) — whether file passed prescreening
- `format` TEXT — PIL mode (e.g. `"RGB"`) or PDF flavor (`"PDF"`/`"PDF/A"`); `"Unreadable"` if the file couldn't be opened/decoded/identified
- `format_issues` TEXT — pipe-delimited, human-readable format/repair/rejection explanations (replaces the old `qa_note`/`qa_parts`)
- `repair_issues` TEXT — comma-separated issue codes (e.g. `"Reject"` or `"Flatten"`)
- `filename_issues` TEXT — human-readable name-parsing / place-validation problems (was `notes`; unrelated to format)

## Prescreener Acceptance Criteria

| Format | Rules |
|--------|-------|
| JPEG | 24-bit RGB, ≤ 100 MB, ≤ 108 MP |
| TIFF | 24-bit RGB or 8-bit grayscale (L), LZW compression (tag 259 = 5), single-frame |
| PDF | Accepted; logs if PDF/A-1b conformance marker is absent |

## Repair Issue Codes

| Code | Meaning | Auto-repairable? |
|------|---------|-----------------|
| `Flatten` | TIFF is RGBA, LA, or I;16 (16-bit grayscale) mode | Yes — dropped to a clean mode (RGB/L) |
| `Compress LZW` | TIFF not using LZW compression | Yes — re-saved with LZW compression |
| `Check MBs` | Uncompressed TIFF exceeds the size limit | Not yet auto-repaired — flagged so a future compress-then-recheck pass can decide; currently always paired with `Compress LZW` |
| `Reject` | Unsupported file type, multi-frame TIFF, PDF lacking a PDF/A-1b conformance marker, or any other oversized/wrong-format file | **No** — must be handled manually via the Reject action |

Issue codes are normalized: lowercase, hyphens → underscores (so `Reject` is matched case-insensitively as `reject`). For a multi-frame TIFF, unsupported file type, or any hard size-limit rejection, `repair_issues` is set to `["Reject"]` only — any other issues detected for that file are discarded in favor of the single `Reject` code.

`iphone_vert` (EXIF-orientation rotation) has been retired from the prescreener's repair_issues vocabulary — it's no longer detected or flagged. The rotation helpers (`_ORIENTATION_ROTATION`, `_DEFAULT_VERT_ROTATION`, `_get_exif_orientation`) remain in `repair_media.py`, unused for now, reserved for planned `Media > Rotate CW / Rotate CCW` menu actions.

## Key Entry Points

- **GUI**: `cdash-digester` (script) or `python -m cdash_digester.gui.main_window`
- **Digester CLI test**: `python -m cdash_digester.digester`
- **Prescreener CLI** (inspect a single file): `python -m cdash_digester.prescreener <filepath>`
- **Repair CLI**: `python -m cdash_digester.repair_media <filepath> <issue_code> [...]`

## Key Dependencies

- `PySide6` — GUI framework
- `Pillow` — image reading, mode checks, frame counting, repair transforms
- `PyMuPDF (fitz)` — PDF metadata and XMP parsing
- `exiftool` (external executable, called via one-shot subprocess in `exiftool_util.read_tags`) — EXIF Orientation, HostComputer, DateTimeOriginal

## Development Notes

- ExifTool must be on PATH for EXIF reads to work.
- Repair backs up originals to a `repaired/` subfolder inside the file's own media folder (`Media/<media-folder>/repaired/`) — but only when a repair is actually committed. A refused (`Reject`) or reverted (still-oversized after `Check MBs` compression) repair leaves the original file completely untouched: no backup, no delete.
- The GUI runs `Digester` methods on a `QThread`; the `log` callback is the only UI coupling.
- `repair_file()` in `repair_media.py` must never attempt to repair `Reject`-flagged files — it returns early with a message pointing at the separate Reject action (`services/reject.py`), which is the only thing that moves/removes a file from the batch.

## Changes to repair_media module.

**Phase C — DONE.** `repair_file()` in `repair_media.py` implements all four bullets below. One deliberate deviation: `Reject` no longer backs up + deletes the file (as it used to) — it leaves the file completely untouched, since the separate Reject action (`services/reject.py`) is now the only thing that moves/removes files from the batch. The backup-then-commit step was restructured to happen only after every refusal/revert check has passed, so a `Check MBs` repair that's still oversized after compression also leaves the file untouched rather than partially applying anything.

These changes are probably mostly in the repair_file module.  The logic is different in the following ways:

* If a file's repair_issue includes "Reject" return with a message saying that the file can't be repaired, and recommend that the use process it with the Reject function. 

* If a file's repair_issue list includes "Flatten", check the mode and decide what the mode should be withuot an alpha channel and return the transformed image with LZW compression.

* If a file repair_issue list includes Compress LZW but not "Flatten" return the image having been re-written with LZW compression. 

* If a media file has a repair issue == "Check Size" check the size against the max value after flattening and compressing.

After all of this, if the size is now within tolerances, copy the original image to the ./repaired folder and replace the original with the current form of the in-memory pil image.
